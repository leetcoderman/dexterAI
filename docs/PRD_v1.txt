ModelForge
AI Model Explorer — Product Requirements Document
Version 1.0  |  February 2026  |  Confidential

Executive Summary
The AI ecosystem is evolving at a pace that creates real cognitive overload for non-technical practitioners — Product Managers, designers, and business operators — who need to stay current without a deep engineering background. ModelForge is a macOS Electron desktop application designed to collapse that gap: a single, structured sandbox where users can connect API keys from any major AI provider, browse models by use-case, and run structured tests with automated evaluation scoring — all without writing a single line of code.

Primary Problem
A PM with minimal dev experience cannot easily test, compare, and evaluate the rapidly expanding catalogue of open-source and commercial AI models available through providers like NVIDIA NIM, Hugging Face, Replicate, Deepgram, Google Gemini, Anthropic, OpenAI, and others. Each provider has different auth methods, SDKs, input schemas, and output formats — making comparison nearly impossible without significant engineering effort.

Step 1 — Feasibility Assessment
Why a Local Electron App?
Electron on macOS is the right architecture for this use case for several reasons:
	•	Secure key storage: API keys can be stored in the OS keychain (via keytar) rather than a remote server, eliminating a critical trust barrier for enterprise users.
	•	Offline-first config: Model registry, connection profiles, and test history are persisted locally using SQLite or LevelDB — no cloud dependency for the app shell itself.
	•	Cross-provider HTTP calls: Electron's Node.js process can make direct HTTP/REST calls to any provider endpoint without CORS restrictions that would block a browser app.
	•	Native file system access: Required for multimodal testing — users can drag-and-drop images, audio files, video clips, and documents directly into the test interface.
	•	Antigravity / custom framework: Using a React-based UI layer within Electron is standard and well-supported on macOS (Apple Silicon + Intel via universal builds).

Step 3 — User Flow & Information Architecture
Screen 1: Home — Use Case Gallery
The home screen presents use-case tiles in a responsive grid (2 columns on 1280px, 3 columns on 1440px+). Each tile shows: category icon, category name, number of connected models, and a 'New' badge if models were added in the last 14 days.
	•	Tile click → navigates to Screen 2 (Model Catalogue) filtered by that category.
	•	A global search bar at the top allows model name search across all categories.
	•	A 'Connected' filter chip shows only categories with at least one verified model.
	•	A notification banner appears when new models are added to the registry (pulled from a remote JSON manifest on app launch if network available).

Screen 2: Model Catalogue
Lists all models within the selected use-case, sorted by release date (newest first) by default. Each row in the list shows: model name, provider logo, release date, parameter count (if public), licence type (open/commercial), and connection status badge (Connected / Not Connected).
	•	Sort options: Release Date, Provider, Popularity (based on star count from Hugging Face API), Licence.
	•	Filter chips: Provider, Licence Type, Local-available.
	•	Click any row → navigate to Screen 3 (API Key Setup).

Screen 3: API Key Setup & Connection Verification
This screen has two states depending on whether the model is already connected.
State A — Not Connected
	•	Provider info card at top: logo, documentation link, pricing tier, rate limits (pulled from registry JSON).
	•	Form field: API Key input (password-masked), with a 'Show' toggle. For providers needing extra config (Org ID, Project ID, region), additional fields appear conditionally.
	•	'Verify Connection' button triggers a minimal test call (e.g., a single-token completion or a models/list endpoint) to confirm the key works. A spinner + progress state shows during the check.
	•	On success: green confirmation banner, key is encrypted and stored in macOS Keychain via keytar. Connection timestamp logged.
	•	'Delete Connection' button (one-click): prompts a single confirmation modal ('Remove API key for [Model]? This cannot be undone.') → deletes from Keychain and resets status to Not Connected.

Step 4 — Test Environment Interface
Layout & Navigation
The test environment uses a two-panel layout: a left sidebar listing all connected models grouped by use-case (collapsible), and a main panel showing the active model's test workspace. A top tab bar allows switching between 'Test', 'History', and 'Evaluation' views for the selected model.
A 'Compare Mode' toggle at the top right activates a split-panel layout where two models can be tested side-by-side with the same inputs — a critical workflow for PM-level evaluation.

Step 5 — Interactive Testing Interface by Model Type
Each use-case category renders a specialised input/output workspace. Below is the full specification:

5.1 Text Generation / Chat
	•	Input panel: Multi-line prompt editor with syntax highlighting, system prompt field (collapsible), conversation history display (chat bubbles), temperature slider (0–2), max tokens input, top-p slider, stop sequences input.
	•	Output panel: Streamed token display with typing indicator, token count live counter, copy button, regenerate button.
	•	Advanced params (collapsed by default): seed, frequency penalty, presence penalty, JSON mode toggle, tool definitions (JSON editor).

5.2 Code Generation
	•	Input: Language selector dropdown, task description text area, optional context code editor (Monaco editor embedded), test input/output pair fields.
	•	Output: Monaco editor with syntax highlighting, copy button, 'Run in sandbox' button (executes safe JS/Python via a sandboxed VM in the Electron main process), diff view against context code if provided.

5.3 Image Generation
	•	Input: Prompt text area, negative prompt field, seed input (with 'Random' button), width/height sliders (constrained to supported aspect ratios), steps slider, guidance scale slider, style preset dropdown (if supported by model).
	•	Output: Generated image displayed in full, download button (PNG/JPEG/WebP), metadata overlay (seed used, actual dimensions), history filmstrip of last 5 generations.

5.4 Image Understanding / VLM
	•	Input: Drag-and-drop or file picker for image (JPG/PNG/WebP/GIF up to 20MB), text question field, detail level toggle (low/high for models that support it).
	•	Output: Text response streamed, bounding box overlay on image if model returns coordinates, copy button.

5.5 Audio Transcription (ASR)
	•	Input: File picker (WAV/MP3/M4A/FLAC/OGG) or live microphone record button (with waveform visualiser), language selector, model-specific options (diarization toggle, punctuation toggle, timestamps toggle).
	•	Output: Transcript text with word-level timestamps (clickable to seek in audio player), confidence scores per segment, speaker labels if diarization enabled, export as SRT/VTT/TXT.

5.6 Text-to-Speech (TTS)
	•	Input: Text area (character count vs model limit), voice selector (dropdown of available voices with preview play), speed slider, pitch slider (if supported), emotion/style selector (if supported).
	•	Output: Inline audio player with waveform, download button (MP3/WAV), playback speed control.

5.7 Embeddings
	•	Input: Single text input or batch mode (CSV upload or line-separated textarea), encoding format selector (float/base64).
	•	Output: Vector display (truncated to first 10 dimensions with 'Show all' toggle), vector dimension count, cosine similarity calculator (paste a second text to compute similarity), visualisation as a heatmap row.

5.8 Object Detection / CV
	•	Input: Drag-and-drop image, confidence threshold slider, NMS (non-max suppression) threshold slider if exposed.
	•	Output: Image with bounding box overlays rendered on canvas, detection results table (class, confidence, coordinates), export as JSON/CSV.

5.9 Video Generation
	•	Input: Text prompt, optional reference image upload, duration selector, aspect ratio selector, motion intensity slider (if supported), seed.
	•	Output: In-app video player with download button (MP4), generation progress bar with estimated time remaining (polling status endpoint), thumbnail preview grid.

6.7 Evaluation History & Comparison
	•	Every test run is saved to local SQLite with all metrics. Users can browse history per model, export as CSV/JSON, or load a past run to compare against a new one.
	•	'Compare' mode renders two runs side-by-side with delta indicators (e.g., +120ms latency, -0.03 cost) highlighted in amber/green.
	•	A summary card shows the model's personal bests: fastest TTFT, lowest cost per 1k tokens, highest throughput.

Step 7 — Later Scope: Local Model Download & Updates
	•	Each model card will display a 'Download Locally' button where applicable (GGUF via llama.cpp, ONNX, or Ollama-compatible models). The button links to the canonical download source (Hugging Face Hub, Ollama registry, NVIDIA NGC).
	•	Local models run via a bundled Ollama sidecar process managed by the Electron main process — no Docker required.
	•	The app checks a versioned remote registry JSON on launch (if online) and surfaces a notification badge when new models or updated quantisations are available.
	•	A 'My Downloads' section in the sidebar shows locally installed models, their disk usage, and version. One-click update pulls the latest quantisation.

Constraints & Risk Register
Constraint / Risk
Severity
Mitigation
API key security: plaintext storage risk
High
Use macOS Keychain exclusively via keytar. Never write keys to disk in plaintext. Show warning if app runs in a non-standard directory.
Provider API breaking changes
Medium
Abstract all API calls behind provider adapters. Version-pin adapter configs. Alert user if a test call returns an unexpected schema.
Rate limits during testing
Medium
Display rate limit headers (x-ratelimit-remaining) in real time. Implement exponential backoff. Show a warning before a call if quota is nearly exhausted.
Model registry staleness
Medium
Registry JSON hosted on GitHub (or CDN). App checks for updates on launch. Fallback to bundled registry if offline.
Video/3D generation latency
Medium
Use async polling pattern with job ID. Show progress bar. Allow user to close and get a desktop notification on completion.
Electron app size / performance
Low-Medium
Lazy-load Monaco editor and waveform libs. Electron builder with ASAR. Target <200MB installer.
macOS notarisation / Gatekeeper
Low
Sign with Apple Developer certificate. Notarise via Apple's notary service in CI/CD pipeline.
CORS / firewall restrictions (enterprise)
Low
All calls made from Electron main process (Node), not renderer. No browser CORS applies. Document proxy config for enterprise firewalls.
Local model resource usage
Low (later scope)
Show system RAM/VRAM requirements before download. Warn if system resources are insufficient.
