Executive Summary
ModelForge is a macOS desktop application built with Electron that gives non-technical AI practitioners — primarily Product Managers — a structured, code-free environment to discover, connect, test, and evaluate AI models from any provider. The ecosystem of open-source and commercial AI models is expanding faster than any individual can track: NVIDIA NIM alone lists 100+ inference endpoints; Hugging Face hosts over 900,000 models. ModelForge collapses the cognitive overhead of this fragmentation into a single, opinionated interface: browse by use-case, enter an API key, press Test, and see exactly how the model performs.

Core Problem Statement
A PM with minimal engineering experience cannot efficiently test, compare, and evaluate the rapidly expanding catalogue of AI models from providers like NVIDIA NIM, Hugging Face, Replicate, Deepgram, Gemini, Anthropic, OpenAI, and others.

Each provider has different authentication methods, input schemas, output formats, and SDK requirements — making structured comparison nearly impossible without significant engineering effort that most PMs cannot perform independently.

Step 1 — Feasibility Assessment
Why Electron + macOS for v1.0
Electron on macOS is the correct architecture for the initial release. The key technical justifications are:
	•	Secure key storage via macOS Keychain (keytar npm package). Keys never touch disk in plaintext — this is a hard requirement given the sensitivity of provider credentials.
	•	All HTTP/REST calls to AI providers are made from the Electron main process (Node.js), meaning there are no CORS restrictions that would block browser-based implementations.
	•	Native file system access: drag-and-drop of audio, image, video, and document files into the test interface is only reliably achievable in a native or Electron context.
	•	The target user demographic (designers, PMs at tech companies) skews heavily toward macOS. This is validated by standard B2B SaaS data: macOS represents 60–70% of knowledge-worker devices at US tech companies.

Framework Clarification: What is Antigravity?
Definition — Antigravity
Antigravity is an internal React-based UI component framework used for this project. It is not a public library.

For all engineering purposes: Antigravity = React 18 + a custom design token system + a set of pre-built UI components (Button, Input, Modal, Toast, etc.) that enforce the ModelForge visual language.

Engineers should treat Antigravity components as they would a customised shadcn/ui or Radix UI library. All components accept standard React props. The component catalogue is documented in /packages/antigravity/README.md in the monorepo.

If Antigravity does not have a component you need, build it in /packages/antigravity/src/components and submit it for review. Do not reach for third-party UI libraries without team discussion.

Platform Scope — macOS v1.0, Cross-Platform Later
Trade-off Decision: macOS-Only for v1.0
ModelForge v1.0 ships as macOS-only (Apple Silicon + Intel universal binary). This is a speed-to-ship decision, not a technical impossibility.

Windows is technically viable: Electron supports Windows natively, and Windows has DPAPI (Data Protection API) for secure credential storage, which keytar supports. Linux has the Secret Service API (libsecret). The reasons for deferring cross-platform are:
  1. Notarisation and code-signing pipelines differ per OS — building for all three triples the release engineering overhead for v1.0.
  2. The primary user demographic (AI-adjacent PMs at US tech companies) is macOS-dominant.
  3. macOS-only lets us dogfood the Antigravity component library on a single platform before adapting to Windows rendering quirks.

Windows support is a firm P2 commitment, not a vague 'maybe later.' The engineering architecture must not make macOS-specific assumptions beyond the Keychain credential store. Use the keytar abstraction layer for all credential operations so the Windows DPAPI path requires only a config change, not a refactor.

Registry Governance
The model registry is the operational backbone of ModelForge. The app is only as useful as the registry is current and accurate. This section defines ownership, schema, update cadence, and stale-data handling.

Registry Schema
The registry is a single versioned JSON file published to a CDN (Cloudflare R2). A bundled fallback copy ships with each app build. Schema:

{
  "registry_version": "2026.02.1",     // CalVer: YYYY.MM.patch
  "generated_at": "2026-02-23T00:00:00Z",
  "models": [
    {
      "id": "llama-3-1-405b-instruct",
      "display_name": "Llama 3.1 405B Instruct",
      "provider_id": "nvidia_nim",
      "category": "text_generation",
      "model_string": "meta/llama-3.1-405b-instruct",
      "release_date": "2024-07-23",
      "param_count_b": 405,
      "context_window": 128000,
      "licence": "llama3.1",             // "open" | "commercial" | named licence
      "licence_type": "open",
      "local_available": true,
      "local_download_url": "https://ollama.com/library/llama3.1",
      "huggingface_id": "meta-llama/Meta-Llama-3.1-405B-Instruct",
      "pricing": {
        "input_per_1m_tokens": 5.00,
        "output_per_1m_tokens": 15.00,
        "currency": "USD",
        "pricing_updated": "2026-01-15",  // Date pricing was last verified
        "pricing_url": "https://..."
      },

Stale Data Handling
	•	On every app launch (if internet available), the app fetches the registry CDN URL with a max-age=3600 cache header. If the remote version is newer than the bundled version, the new registry is downloaded and cached locally.
	•	If the fetch fails (offline, CDN down), the app falls back to the cached local registry and shows a subtle 'Registry last updated X days ago' indicator in the footer.
	•	If pricing data is older than 30 days, the cost estimate in the evaluation panel shows an amber '~ estimated' badge with a link to the provider pricing page rather than a confident number.
	•	If a model's pricing_updated date is more than 90 days old, the cost estimate column is hidden entirely and replaced with a 'Pricing unverified — check provider' link.

Step 3 — User Flow & Onboarding
First-Run / Onboarding Flow (New Requirement)
The first-launch experience for a user with zero connected providers must be explicitly guided. A blank home screen showing 13 tiles all reading '0 connected models' is confusing and demotivating for a non-technical user.

Onboarding Flow — 4 Steps
Step 1 — Welcome screen: App name, one-sentence value prop, 'Get started' CTA. Skip option for returning users (cookie-persisted).

Step 2 — Choose a use case: User picks their first category (image gen, chat, transcription, etc.). This anchors the experience to something they care about.

Step 3 — Connect your first provider: Filtered view of providers for that category, sorted by 'easiest to get a free API key.' Each provider card links directly to their key generation page. API key input form + Verify button.

Step 4 — Run your first test: After successful verification, the app auto-navigates to the test workspace pre-loaded with a starter prompt appropriate to the category. A tooltip overlay highlights the key controls.

	•	'New badge' threshold: Changed from arbitrary '14 days' to 'since the user's last app launch' — more meaningful and personalised.
	•	Returning users with no connections land on the Home screen with an ambient nudge: 'Connect your first model to start testing' in the hero area. No forced modal.

Screen 1: Home — Use-Case Gallery
	•	Responsive grid of 13 category tiles. Each tile: category icon, name, connected model count badge, 'New' indicator if models added since last launch.
	•	Global search bar searches across model names, providers, and tags.
	•	'Connected only' filter chip shows categories with at least one verified connection.
	•	Network-fetched registry update notification bar appears at top if a newer registry version is available.

Screen 2: Model Catalogue
	•	Models listed for the selected category, sorted by release date (newest first) by default.
	•	Each row: model name, provider logo, release date, parameter count, licence type, connection status badge.
	•	Sort: Release Date, Provider, Popularity (via Hugging Face likes API, fetched on load, cached 24h with a single authenticated HF token bundled in app), Licence.
	•	Filter chips: Provider, Licence (open/commercial), Local-available.
	•	Note on HF popularity fetch: the app uses a single read-only HF API token bundled at build time (not user-provided) to call the /api/models?sort=likes endpoint. This token has no write access and is rate-limited to 1,000 requests/hour — the app caches results per session to stay well within limits.

Screen 3: API Key Setup & Connection Verification
State A — Not Connected
	•	Provider info card: logo, docs link, pricing link, status page link, free tier indicator.
	•	API key input (password-masked field, with Show toggle).
	•	Conditional additional fields appear based on provider connection_config: org_id for OpenAI, project_id for Vertex AI, etc. Fields are labelled clearly with inline help text.
	•	'Verify Connection' button: triggers a minimal, low-cost test call (e.g., GET /models or a 1-token completion). Spinner + 'Verifying...' state during check.
	•	On success: key encrypted and stored in macOS Keychain via keytar. Connection timestamp logged to local SQLite.
	•	One-click delete: 'Disconnect' button with a single confirmation modal. Removes from Keychain and resets status.

Prompt Template Library — Reclassified to P0
Priority Change
The prompt template library was P2 in v1.0. It is reclassified to P0 for v2.0.

Rationale: The primary persona (Alex the PM) will repeatedly run the same evaluation prompt across multiple models in the same session. Without a save mechanism, they must retype the same prompt 5–10 times. This is the single highest-friction point in the core test loop.

MVP implementation: A 'Save as Template' button in every prompt input field. Templates are named, stored locally in SQLite, and shown in a dropdown above the prompt field. One-click load. One-click delete. Templates are scoped to a category (a text gen template is not shown in the image gen workspace).

Step 5 — Interactive Test Workspaces by Category
5.1 Text Generation / Chat
	•	Inputs: Prompt editor (resizable, multi-line), system prompt field (collapsible), conversation history (chat bubble thread), temperature slider (0.0–2.0, step 0.1), max tokens input, top-p slider, stop sequences input.
	•	Output: Streamed token display with live token counter. Regenerate button. Copy button.
	•	Advanced (collapsed by default): seed, frequency penalty, presence penalty, JSON mode toggle, response_format selector (text / json_object), tool definitions (Monaco JSON editor).

5.2 Code Generation
	•	Inputs: Language selector, task description textarea, optional code context pane (Monaco editor, syntax highlighted), test input/output pair fields.
	•	Output: Monaco editor (read-only) with syntax highlighting. Copy button. Diff toggle shows changes vs. input context code.
Code Execution — Security Decision
v1.0 PRD proposed a 'Run in sandbox' button using a Node.js sandboxed VM. This is DEFERRED to P3.

Reason: No Node-based sandbox (vm2, isolated-vm) is appropriate for executing arbitrary LLM-generated code in a production desktop app without a formal security review. vm2 has active CVEs. isolated-vm is safer but requires native compilation which complicates the Electron build.

P3 approach (when implemented): Code execution will use WebAssembly-based sandboxing (Pyodide for Python, QuickJS for JS) which runs in a separate renderer process with context isolation and no Node.js API access. This will go through a security review before shipping.

v1.0 replacement: A 'Copy to clipboard' button with a tooltip 'Paste this into your IDE or a Jupyter notebook to run.' This is honest about the current capability and sets correct expectations.

5.3 Image Generation
	•	Inputs: Prompt textarea, negative prompt textarea, seed (number input + Random button), width/height sliders (constrained to model-supported aspect ratios from registry), steps slider, guidance scale slider, style preset dropdown (if model supports it).
	•	Output: Generated image (full-width display), download button (PNG/JPEG/WebP), metadata overlay (seed used, final dimensions), generation history filmstrip (last 5 results, clickable to restore params).

5.4 Image Understanding / VLM
	•	Inputs: Image drop zone (JPG/PNG/WebP/GIF, max 20MB), text question field, detail level toggle (low/high where supported).
	•	Output: Streamed text response. If model returns bounding box coordinates (YOLO format or COCO JSON), the app renders them as an SVG overlay on the displayed image.

5.5 Audio Transcription (ASR)
	•	Inputs: File picker (WAV/MP3/M4A/FLAC/OGG/OPUS) or live microphone record button with waveform visualiser (Web Audio API). Language selector. Model-specific toggles: diarization, punctuation, timestamps, smart_format.
	•	Output: Transcript text. If timestamps returned, words are clickable and seek the audio player to that position. Speaker labels displayed if diarization enabled. Export: SRT / VTT / plain TXT.

5.6 Text-to-Speech (TTS)
	•	Inputs: Textarea (shows character count vs. model limit). Voice selector (dropdown with preview play button per voice). Speed slider. Pitch slider (if supported). Emotion/style selector (if supported by model).
	•	Output: Inline audio player with waveform. Download button (MP3/WAV). Playback speed control (0.5x–2x).

5.7 Embeddings / Semantic Search
	•	Inputs: Single text input, or batch mode (CSV upload or line-separated textarea). Encoding format selector (float/base64/int8 where supported).
	•	Output: Vector preview (first 10 dimensions, 'Show full vector' toggle). Dimension count. Cosine similarity calculator: paste a second string to compute similarity inline. Heatmap row visualisation.

5.8 Reranking
	•	Inputs: Query string. Candidate passages (add/remove textarea rows, or CSV import). Top-N selector.
	•	Output: Ranked table with original rank, new rank, relevance score. Score delta column (green/red).

5.9 Object Detection / CV
	•	Inputs: Image drop zone. Confidence threshold slider (0.0–1.0). NMS threshold slider (if exposed by model).
	•	Output: Canvas with bounding box overlays (colour-coded by class). Detection results table (class, confidence, x1/y1/x2/y2). Export as JSON (COCO format) or CSV.

5.10 Video Generation
	•	Inputs: Text prompt. Optional reference image. Duration selector. Aspect ratio selector. Motion intensity slider (if supported). Seed input.
	•	Output: Async job with polling. Progress bar + estimated time. Desktop notification on completion (using Electron's Notification API). In-app video player. Download button (MP4). Thumbnail grid of last 3 generations.

5.11 Music / Audio Generation
	•	Inputs: Text prompt describing style/mood/instrumentation. Duration selector (5s–60s). Seed. Optional melody conditioning input (audio file upload, if supported by model).
	•	Output: Inline audio player with waveform. Download as WAV/MP3. Metadata overlay (BPM, key if returned).

5.12 3D Generation
	•	Inputs: Text prompt or reference image upload. Quality preset (fast/balanced/high).
	•	Output: A 3D viewer (Three.js in a renderer iframe, context-isolated). Orbit controls for rotation. Download as .obj or .glb. Polygon count display.

  reset()
  const requestId = crypto.randomUUID()

    appendChunk(chunk)  // Zustand setter — triggers React re-render

    finalise(metrics)
    unsub1(); unsub2(); unsub3()

    setError(err)
    unsub1(); unsub2(); unsub3()
  })

  await window.modelforge.provider.test({ requestId, modelId, params, category })
}

T3 — Backend Engineering Specification (Electron Main Process)
In Electron, the 'backend' is the main process. It has full Node.js access and is the only process that performs I/O, storage, and network operations. Treat it with the same discipline you would apply to a production API server.

T3.1 — ProviderAdapter Architecture
All AI provider calls go through a ProviderAdapter. No provider-specific code lives outside of its adapter file. This is the most important architectural constraint in the codebase.

// main/adapters/base.adapter.ts
abstract class BaseProviderAdapter {
  abstract readonly providerId: string

  // Called during API key verification
  abstract verify(credentials: ProviderCredentials): Promise<VerifyResult>

  // Called to execute a test. Must emit IPC events as results arrive.
  abstract execute(request: TestRequest, credentials: ProviderCredentials,
                   emitter: IPCEmitter): Promise<void>

  // Shared retry logic with exponential backoff
  protected async withRetry<T>(
    fn: () => Promise<T>,
    maxAttempts = 3,
    baseDelayMs = 1000
  ): Promise<T> {
    for (let attempt = 1; attempt <= maxAttempts; attempt++) {
      try {
        return await fn()
      } catch (err) {
        if (err.status === 429) {
          const retryAfter = parseInt(err.headers['retry-after'] ?? '1') * 1000
          const delay = Math.max(retryAfter, baseDelayMs * Math.pow(2, attempt - 1))
          if (attempt < maxAttempts) await sleep(delay)
        } else if (attempt === maxAttempts || !isRetryable(err.status)) {
          throw err
        }
      }
    }
  }

  // Shared rate limit header extraction
  protected extractRateLimit(headers: Headers): RateLimitInfo {
    return {
      remaining: parseInt(headers.get('x-ratelimit-remaining-requests') ?? '-1'),
      resetAt: headers.get('x-ratelimit-reset-requests') ?? null,
      limitType: 'requests'
    }
  }
}

// Example concrete adapter
// main/adapters/anthropic.adapter.ts
class AnthropicAdapter extends BaseProviderAdapter {
  readonly providerId = 'anthropic'
  private client: Anthropic | null = null

  private getClient(apiKey: string): Anthropic {
    // Instantiate client with key from Keychain — never stored as class state
    return new Anthropic({ apiKey })
  }

  async verify(creds: ProviderCredentials): Promise<VerifyResult> {
    try {
      const client = this.getClient(creds.apiKey)
      await client.models.list()  // Lightweight verify call
      return { success: true }
    } catch (err) {
      return { success: false, error: mapAnthropicError(err) }
    }
  }

  async execute(req: TestRequest, creds: ProviderCredentials, emit: IPCEmitter) {
    const client = this.getClient(creds.apiKey)
    const params = req.params as TextGenParams
    const startTime = performance.now()
    let firstChunkTime: number | null = null

    const stream = await this.withRetry(() =>
      client.messages.stream({
        model: req.modelId,
        max_tokens: params.maxTokens,
        messages: buildMessages(params),
        system: params.systemPrompt,
        temperature: params.temperature,
        stream: true
      })
    )

    for await (const event of stream) {
      if (event.type === 'content_block_delta' && event.delta.type === 'text_delta') {
        if (!firstChunkTime) firstChunkTime = performance.now()
        emit('test:chunk', { requestId: req.requestId, text: event.delta.text })
      }
    }

    const finalMsg = await stream.finalMessage()
    emit('test:done', {
      requestId: req.requestId,
      ttft: firstChunkTime ? firstChunkTime - startTime : null,
      totalTime: performance.now() - startTime,
      promptTokens: finalMsg.usage.input_tokens,
      completionTokens: finalMsg.usage.output_tokens,
      finishReason: finalMsg.stop_reason,
      cacheReadTokens: finalMsg.usage.cache_read_input_tokens ?? 0
    })
  }
}

T3.2 — IPC Handler Registration
// main/ipc/provider.ipc.ts
import { ipcMain } from 'electron'
import { AdapterRegistry } from '../adapters/adapter-registry'
import { CredentialStore } from '../credentials/credential-store'

export function registerProviderHandlers(emitter: IPCEmitter) {
  ipcMain.handle('provider:verify', async (_, providerId: string, modelId: string) => {
    const adapter = AdapterRegistry.get(providerId)
    const credentials = await CredentialStore.get(providerId)
    return adapter.verify(credentials)
  })

  ipcMain.handle('provider:test', async (event, request: TestRequest) => {
    const adapter = AdapterRegistry.get(request.modelId)  // mapped via registry
    const credentials = await CredentialStore.get(adapter.providerId)

    // Store AbortController so we can cancel in-flight requests
    const abort = new AbortController()
    ActiveRequests.set(request.requestId, abort)

    try {
      await adapter.execute(request, credentials, emitter)
    } catch (err) {
      emitter.emit('test:error', { requestId: request.requestId, ...mapError(err) })
    } finally {
      ActiveRequests.delete(request.requestId)
    }
  })

  ipcMain.handle('provider:cancel', async (_, requestId: string) => {
    ActiveRequests.get(requestId)?.abort()
  })
}

T3.3 — Credential Store
// main/credentials/credential-store.ts
import keytar from 'keytar'

const SERVICE_NAME = 'modelforge'

export const CredentialStore = {
  // Account key format: '{providerId}:{appInstanceId}'
  // appInstanceId = machine-unique UUID generated on first launch, stored in app userData
  // This namespacing prevents credential collisions if multiple users share a machine

  async save(providerId: string, apiKey: string, extras?: Record<string,string>) {
    const account = buildAccount(providerId)
    // Main credential
    await keytar.setPassword(SERVICE_NAME, account, apiKey)
    // Extra fields (org_id, project_id, etc.) stored as separate entries
    if (extras) {
      for (const [key, value] of Object.entries(extras)) {
        await keytar.setPassword(SERVICE_NAME, `${account}:${key}`, value)
      }
    }
  },

  async get(providerId: string): Promise<ProviderCredentials> {
    const account = buildAccount(providerId)
    const apiKey = await keytar.getPassword(SERVICE_NAME, account)
    if (!apiKey) throw new Error(`No credentials found for provider: ${providerId}`)
    // NOTE: This method is only callable from the main process.
    // The preload script does NOT expose getPassword to the renderer.
    return { apiKey, extras: await getExtras(account) }
  },

  async delete(providerId: string) {
    const account = buildAccount(providerId)
    await keytar.deletePassword(SERVICE_NAME, account)
    // Delete all extra field entries too
    const allCreds = await keytar.findCredentials(SERVICE_NAME)
    for (const c of allCreds.filter(c => c.account.startsWith(`${account}:`))) {
      await keytar.deletePassword(SERVICE_NAME, c.account)
    }
  },

  async exists(providerId: string): Promise<boolean> {
    return !!(await keytar.getPassword(SERVICE_NAME, buildAccount(providerId)))
  }
}

T3.5 — Registry Fetch & Cache
// main/registry/registry-manager.ts
const REGISTRY_CDN_URL = 'https://registry.modelforge.app/registry.json'
const REGISTRY_CACHE_PATH = path.join(app.getPath('userData'), 'registry-cache.json')
const BUNDLED_REGISTRY_PATH = path.join(__dirname, '../../registry/registry.json')

export async function loadRegistry(): Promise<Registry> {
  // 1. Try remote registry
  try {
    const response = await fetch(REGISTRY_CDN_URL, {
      headers: { 'Cache-Control': 'max-age=3600' },
      signal: AbortSignal.timeout(5000)  // 5s timeout; don't block app launch
    })
    if (response.ok) {
      const remote = await response.json() as Registry
      if (isNewerVersion(remote.registry_version, getCachedVersion())) {
        await fs.writeFile(REGISTRY_CACHE_PATH, JSON.stringify(remote))
        return remote
      }
    }
  } catch {
    // Network unavailable — fall through to cache
  }

  // 2. Try local cache
  try {
    const cached = JSON.parse(await fs.readFile(REGISTRY_CACHE_PATH, 'utf8'))
    return cached
  } catch {
    // No cache — fall through to bundled
  }

  // 3. Bundled fallback (always present)
  return JSON.parse(await fs.readFile(BUNDLED_REGISTRY_PATH, 'utf8'))
}

    properties: ['openFile'],

  })

  return result.filePaths[0]  // Absolute path returned to renderer
  // The actual file read happens in the adapter when execute() is called
})

  const result = await dialog.showOpenDialog({
    properties: ['openFile'],
    filters: [{ name: 'Image', extensions: ['jpg','jpeg','png','webp','gif'] }]
  })
  return result.canceled ? null : result.filePaths[0]
})

// For drag-and-drop: renderer receives the file path from the DragEvent.
// It sends the path to main via IPC. Main validates the extension
// against the allowed list before reading the file.

function validateFileExtension(filePath: string, allowedExtensions: string[]): boolean {
  const ext = path.extname(filePath).toLowerCase().slice(1)
  return allowedExtensions.includes(ext)
}
